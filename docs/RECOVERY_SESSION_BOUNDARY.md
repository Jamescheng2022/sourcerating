# Password recovery stays bound to its own account

The former reset page treated any existing project session as proof of a valid recovery link. The installed Supabase SDK deliberately retains an existing login when a callback fails. As a result, opening an expired link while signed in exposed a password-change form for the existing account. The browser regression reproduced this on the unchanged application baseline `7373290ea857db950cfb1c9873a0a63dd4839a1b` before the fix.

The reset page now uses the existing Supabase SDK with a separate session key and tab-scoped `sessionStorage`. Only this client consumes `/reset-password` callback credentials; the normal project client disables callback detection on that route, including when Next preloads its module. This is needed because a browser test demonstrated that preloading could otherwise replace the project login with the recovery account.

Supabase continues to verify tokens and authorize password updates. Recovery callbacks use the existing implicit recovery-link format; no new authentication server, provider, credential or database policy is introduced. A failed, reused, malformed or different-type callback clears the older recovery session and never falls back to project storage. A validated recovery survives reload in that tab. Storage/provider failure gives a fresh-link path. The form shows the account being changed, and switching the project account in another tab does not retarget it.

After a successful password update, recovery credentials are cleared. If the subsequent provider logout fails, the page reports that the password changed and server revocation was not confirmed; it does not falsely report that the password update failed or that other sessions ended. An unrelated project login remains intact. This separation is a UI/session boundary, not a replacement for server authorization or proof that every existing access token is immediately invalidated by logout.

The `recovery-boundary` acceptance mode uses synthetic local Auth accounts, local Mailpit capture and two normal project accounts. HTTP failure responses for password update/logout are isolated fixtures. The existing `recovery` mode checks actual successful update/logout, old-password denial and server password policy. Neither establishes real external email or public-preview acceptance. Original invitation/file-gateway tests remain blocked until the separately approved `kong` policy is applied and verified; this work does not retry them.
