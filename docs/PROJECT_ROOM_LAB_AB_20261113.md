# Project Room Lab｜独立前端实验与 A/B 对比报告

**日期：** 2026-11-13　**分支：** `experiment/claude-frontend-comparison-20261113`（基于 `pilot/real-ai-acceptance-20261028` @ `f644534`）
**预览路由：** `/project-room-lab`（B）　对照：`/project-room`（A，未改动）

> B 全部运行在明确标记的 DEMO 数据上，不连接 Supabase，不调用模型。本报告中凡是“演示”的地方都不是真实后端结果。

---

## 1. 结论

**选 B：保留现有技术栈和全部后端，大幅重构 Project Room 的表现层。不选 C。**

- 现有 Pilot 对 ChatScope 的实际使用只有 `Message` 和 `MessageSeparator` 两个组件，另加 8 处 `:global(.cs-*)` 覆盖样式。聊天列表、输入框、滚动、附件、搜索都已经是自己写的。所以“换一套聊天 UI 库”换不到什么，反而再绑定一套别人的 DOM 和样式。
- SourceRating 的差异化（组织身份、内外部边界、证据回溯、AI 私有面板、文件版本）没有任何聊天 UI 库提供，必须自己掌握。
- 该复用的是**无样式的底层原语**：虚拟列表（react-virtuoso）和无障碍交互（Radix）。这两类自己写最容易出错，升级成本也最低。
- 现有 `src/lib/*`（会话、消息去重与补洞、待发消息持久化、文件上传与校验、提案审核）质量不错，应原样保留，B 的结构通过一个适配层接上去。

**B 是否真的更好：** 在交互模型、消息列表规模、代码结构上有可测量的证据（第 6 节）。在生产就绪度上 A 领先：A 接了真实后端、实时、文件校验，B 目前只是 DEMO 数据上的原型。

## 4. 设计方案

一句话：**默认只有“列表 + 聊天”，其余一切按需出现。**

| 区域 | 设计 | 理由 |
|---|---|---|
| 左侧 | 顶部是**组织身份切换**（谁在说话）；搜索；`全部 / 待你处理 / 未读`；房间按项目分组；每行显示对方组织；内部房间用琥珀色锁 | 一眼分清“我代表谁、在和谁合作、哪些只有内部可见” |
| 中间 | 自己的消息靠右；他人消息带姓名 + 组织色标；回复引用可点回原文；文件卡片带版本；语音带转写；译文以虚线框显示在气泡内 | 沿用微信/WhatsApp 习惯，不需要学习 |
| 消息操作 | 桌面悬停出现 `回复 / 问 AI / 翻译 / ⋯`；右键同一菜单；触屏是气泡旁一个 `⋯`，长按亦可 | 不放大按钮；操作随消息类型变化（文件多出预览、比较版本、相关消息） |
| 右侧 | **默认关闭**。五个 Tab：概览、待确认、文件、成员、AI | 普通聊天不被打扰 |
| AI | 待确认数量只是标题栏一个安静的数字；问 AI 的结果进私有面板，标明“仅你可见”，带来源；要发到群里必须自己点“放进输入框”再发送 | AI 不替用户说话 |
| 证据 | 每条 AI 整理的事项都有来源标签，点击回到原始消息并高亮；确认后，原始消息下方出现“已记录”标记，可反向打开记录；每条消息可复制深链 | 双向可追溯 |
| 视觉语言 | 虚线边框 = 仅你可见 / 尚未确认；琥珀色 = 内部；组织色标 = 身份 | 用布局和三种固定记号说话，少写说明文字 |

**响应式：**

| 宽度 | 布局 |
|---|---|
| ≥1100 | 列表 304 + 聊天 + 面板 368（按需打开，聊天让位） |
| 700–1099 | 列表 272 + 聊天并排；面板是右侧抽屉，**覆盖而不挤压**聊天 |
| <700 | 单栏：房间列表页 → 聊天页（浏览器返回键可回列表）；面板是 Bottom Sheet；文件预览全屏 |

**对“三栏是否仍是最好方案”的回答：** 三栏作为“最大展开状态”是对的，但不应是默认状态。现有 A 在桌面默认三栏全开，右栏常驻 AI 助理、里程碑、摘要、Needs You，聊天只占 808px（1440 宽）。B 默认两栏，第三栏由具体意图触发（点了问 AI、点了待确认、点了成员），这更接近成熟聊天软件“点开详情才出现侧栏”的习惯。

## 7. 对八个问题的回答

1. **既像聊天软件又能承载复杂协作？** 聊天区只放聊天。复杂性放进三个地方：消息自己的菜单、按需打开的侧栏、消息下方一行安静的“已记录”。业务对象从聊天里长出来，由人确认，不要求用户先填表。
2. **三栏是否最好？** 作为上限是，作为默认不是。见第 4 节。
3. **ChatScope 是否值得继续？** 不值得。只用了 2 个组件，18 个月没有发布，还带着 FontAwesome。也不建议换成 MinChat 或任何整套聊天 UI 库。
4. **自建多少、复用多少？** 行为原语全部复用（滚动、焦点、菜单、弹层），业务外观全部自建。B 的 1,783 行里没有一行在实现虚拟滚动或焦点管理。
5. **如何保证几年后还能升级？** ① 依赖只选无样式原语，升级不影响外观；② 第三方组件只通过 `components/ui/*` 和 `RoomDataSource` 两个边界进入，业务组件不直接 import；③ 精确锁版本，每增加一个依赖写明解决什么问题；④ 保留浏览器验收脚本，升级后跑一遍。
6. **哪些值得保留？** `src/lib/` 全部：`demo-session.ts`（去重与补洞）、`pending-message.ts`、`room-files.ts`（上传与校验）、`project-state.ts`、`staging.ts`、`ai/runtime.ts`、`room-archive.ts`；`evidence-downloads.tsx`、`ai-settings.tsx`；视口高度跟踪和输入法处理的做法；文件校验状态的展示（B 应补上）；现有 Playwright 验收脚本。
7. **新前端是否真的更好？** 交互和结构上有证据（第 6 节）；生产就绪度上不是。它是一个值得照此重构的方向，不是可以直接替换的成品。
8. **长期架构？** Next + React + TypeScript + Tailwind 4 不变；Radix 原语 + 自有 `components/ui`；react-virtuoso；一个 `RoomDataSource` 接口（Supabase 实现 + Demo 实现，后者同时服务验收测试）；接后端时加 TanStack Query；AI 流式面板做真的时候再评估 assistant-ui。

| 4 | 文件：真实卡片（含校验状态）、签名链接预览（图片、PDF 用 pdf.js）、按 `logical_name` 比较版本 | 中 |
